# V4 P0/P1 负载零值统计勘误

基于冻结正式 Train 的 30 个样本、第 40 轮 greedy Train 归档和正式执行代码独立核算。复算入口：`PYTHONPATH=src python scripts/audit_v4_train_load_mapping.py`。脚本仅调用 `load_train()`，校验五份 manifest SHA256 与归档 `run_metadata.json` 一致，逐条校验 15119 个已执行 transition 与原始 ONBOARD 行的映射；`opened_test_payloads=0`。未改原始数据及旧归档。

## 差异来源

正式加载器将 1 s 功率 CSV 的 30 s 控制点原样放入 `episode.load_kw`，包括 `[-1,0)` kW 的微小负值；`normalize_onboard_load_kw` 按冻结的 1 kW 源负载死区把这些值映射为有效 0 kW。V4 每步先规范化再求物理掩码和执行；归档 `load_kw` 是 `P_Bat+P_FC`，即**执行后的有效负载**，不是原始 CSV 的 `load_total_kw`。逐步核对，归档有效负载与相应原始行规范化值 15119/15119 一致。

| 口径 | ONBOARD 点 | 原始精确 0 | 原始 `0<L<10` | 原始负值 | 执行有效 0 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 全部正式 Train | 18448 | 30 | 457 | 2070 | 2100 |
| 第40轮已执行 greedy 前缀 | 15119 | 30 | 451 | 2070 | 2100 |

具体映射：`zero_boundary_029` 的归档 transition **355**（从 0 起）对应模式/监督行 **355**、`time_s=10650`，原始功率文件 `data/processed/operating_dataset_zero_boundary_v2/train/zero_boundary_029.csv` 的 0 起数据行 **10650**、含表头的 1 起文件行 **10652**。原始 `load_total_kw=-0.086894`，执行有效负载和归档 `load_kw` 均为 **0**。归档索引只计已执行 ONBOARD 动作；对应方式是样本中第 *j* 个 ONBOARD 原始监督行（岸电行跳过）。完整行号由复算脚本输出。

## 对 P0/P1 结论的影响

- 第40轮 `SOC_before≥0.79、FC=0` 共 **2607** 个已执行步；其中物理掩码仅 `{0}` **2372** 步，有正功率可行仍选 0 **235** 步。2372 步中，原始负值规范化为 0 的有 **2057** 步，原始精确零值 **0** 步，原始 `0<L<10` 有 **315** 步。P1 所写“负载严格为 0 的 2057 步”应读作**执行模型的有效负载严格为 0**，不能读作原始测量负载恰好为 0。
- P0 的 326 次 0→正功率启动、62 次各航段首次启动（其中 8 次延后）、264 次同段内部重启，以及 2372/235 物理掩码分组，经归档重新计数仍成立。P0/P1 关于**执行模型**中高 SOC、10 kW 动作网格与受迫停机的结论仍成立；如果把它们外推为“实测原始零负载导致停机”则不成立。
- `docs/v4_high_soc_reward_failure_diagnostic_2026-10-09.md` 第20、43行与 `docs/v4_scheme_a_design_test_prep_2026-10-09.md` 第9行的“零负载/负载为0”缺少“有效”限定。本勘误保留原报告和历史归档，不改写证据。控制模型输入及掩码使用同一规范化值，未发现字段错位或数据漂移，可进入方案 A 实施。

这项死区是既有冻结数据处理规则，不代表设备可测得真实零负载。方案 A 仍应把执行有效 0 kW 时的正功率物理可行性作为动作门控依据，不得自行修改该规则。
